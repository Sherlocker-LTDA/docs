As APIs da **Plataforma** usam uma chave de API com escopos por produto. A chave
identifica o workspace, limita as ações permitidas e permite rastrear quem criou
cada recurso.

<Warning>
  **Implementação local em revisão.** As migrations não foram aplicadas e não há
  disponibilidade observada em produção para os endpoints desta seção. Confirme
  a habilitação observada do produto e do workspace antes de integrar.
</Warning>

## Base da API

Use a base externa canônica em todas as chamadas:

```text
https://api.sherlocker.com.br/api/v1
```

Os caminhos `/v1` existentes no backend são internos. A presença de uma rota
interna não significa que ela já foi publicada no host externo.

## Enviar a chave

Envie a chave no header `Authorization`:

```bash
curl https://api.sherlocker.com.br/api/v1/dossies \
  -H "Authorization: Bearer slhk_sua_chave_aqui"
```

Não envie a chave em query string, corpo, logs ou código client-side.

<Note>
  As chaves `slhk_` já emitidas para `/analyses` e `/operations` continuam
  limitadas a essas rotas. As novas APIs de produto exigem uma chave scoped,
  emitida com workspace, scopes e entitlements explícitos.
</Note>

## Scopes por produto

| Produto       | Leitura         | Escrita ou execução         |
| ------------- | --------------- | --------------------------- |
| Dossiê        | `dossies:read`  | `dossies:write`             |
| Monitoramento | `monitors:read` | `monitors:write`            |
| Rastro        | `rastro:read`   | `rastro:search`             |
| Board e Mapa  | `boards:read`   | `boards:write`              |
| Lente         | `lente:read`    | `lente:geo` ou `lente:face` |

Um scope de escrita **não** implica leitura. Por exemplo, uma chave com apenas
`dossies:write` pode criar um Dossiê, mas não consultar seu resultado.

O scope de leitura do produto libera o resultado completo e os artefatos daquele
produto. A v1 não usa scopes adicionais como `pii:read` ou `artifacts:read`.

## Workspace e ownership

Todo recurso novo pertence ao workspace da chave. IDs de usuário e da própria
chave registram a origem técnica, mas não mudam o ownership.

- Toda leitura e mutação é filtrada pelo `workspace_id` derivado da chave.
- Um ID inexistente ou pertencente a outro workspace retorna o mesmo
  `404 resource_not_found`.
- Outra chave válida do mesmo workspace, com scope de leitura, pode recuperar
  recursos e artefatos criados pela chave original.
- Revogar uma chave bloqueia novas chamadas, mas não cancela trabalho já aceito
  nem gera refund automático.

Nenhuma API pública confia em headers de identidade enviados pelo cliente. O
workspace e o ator são sempre derivados da credencial.

## Finalidade (`purpose_id`)

Criações de Dossiê, Monitor, Rastro e Lente exigem um `purpose_id` ativo,
previamente aprovado para o produto no mesmo workspace. Board e Mapa não exigem
finalidade por mutação.

```json
{
  "purpose_id": "11111111-1111-4111-8111-111111111111"
}
```

O `purpose_id` é validado antes de criar recurso, cobrar ou enfileirar trabalho e
faz parte do fingerprint de idempotência. A API v1 não oferece CRUD público de
finalidades.

| Situação                                            | Resposta                  |
| --------------------------------------------------- | ------------------------- |
| campo ausente                                       | `422 purpose_required`    |
| finalidade inativa ou não habilitada para o produto | `422 purpose_not_allowed` |
| finalidade pertencente a outro workspace            | `404 resource_not_found`  |

Inativar uma finalidade bloqueia novas coletas e retries. Recursos já aceitos
continuam legíveis e preservam a finalidade usada no momento da criação.

## Idempotência

Todo `POST` faturável de criação ou retry exige `Idempotency-Key`. Gere uma key
única por intenção de negócio e persista o ID público retornado.

```bash
curl -X POST https://api.sherlocker.com.br/api/v1/rastro/searches \
  -H "Authorization: Bearer slhk_sua_chave_aqui" \
  -H "Idempotency-Key: 123e4567-e89b-42d3-a456-426614174000" \
  -H "Content-Type: application/json" \
  -d '{
    "type": "email",
    "target": "contato@example.com",
    "strategy": "all",
    "purpose_id": "11111111-1111-4111-8111-111111111111"
  }'
```

| Situação                                                | Comportamento                                                                                        |
| ------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| primeira requisição aceita                              | retorna `201` ou `202`, recurso e `Location`                                                         |
| mesma key e mesmo fingerprint                           | repete o status e o corpo lógicos, sem novo recurso ou cobrança; inclui `Idempotency-Replayed: true` |
| mesma key enquanto a primeira persistência não terminou | `409 idempotency_in_progress` e `Retry-After`                                                        |
| mesma key com conteúdo diferente                        | `409 idempotency_conflict`                                                                           |
| key ausente quando obrigatória                          | `400 idempotency_key_required`                                                                       |

O fingerprint inclui workspace, rota, versão do contrato e todos os campos que
alteram preço ou resultado, inclusive `purpose_id`. O registro concluído pode ser
reproduzido por no mínimo 24 horas.

<Warning>
  Duas `Idempotency-Key` diferentes criam recursos, execuções e cobranças
  diferentes, mesmo quando o corpo é idêntico. Um cache interno de fonte não
  transforma uma nova intenção em replay.
</Warning>

## Três eixos independentes

Não deduza resultado ou cobrança apenas pelo campo `status`:

| Eixo                                 | Pergunta respondida                                | Exemplos                                      |
| ------------------------------------ | -------------------------------------------------- | --------------------------------------------- |
| `status`                             | o recurso ainda está sendo processado?             | `queued`, `running`, `completed`, `failed`    |
| `result.outcome` e `coverage.status` | o que foi encontrado e quão completa foi a coleta? | `full`, `partial`, `no_match`, `inconclusive` |
| `billing.status`                     | houve cobrança ou refund?                          | `charged`, `refund_pending`, `refunded`       |

Um resultado negativo válido, como `not_found`, `no_match` ou `no_face`, não é
erro HTTP. Depois que um recurso foi aceito, uma falha de provider ou executor
aparece no próprio recurso com HTTP `200` e `status: "failed"`.

## Formato das respostas

- JSON em `snake_case`, UTF-8 e timestamps ISO 8601 em UTC.
- Toda resposta inclui o header `x-request-id`.
- Recursos singulares não usam envelope `{ data: ... }`.
- Coleções usam `data` e `page` com cursor opaco.
- Paginação usa `limit=20` por padrão e aceita no máximo `100` itens.
- O cursor é vinculado ao workspace, rota, filtros e snapshot da listagem.

```json
{
  "data": [],
  "page": {
    "next_cursor": null,
    "has_more": false
  }
}
```

## Problem Details

Erros usam `Content-Type: application/problem+json`:

```json
{
  "type": "https://docs.sherlocker.com.br/problems/validation_error",
  "title": "Validation Error",
  "status": 400,
  "code": "validation_error",
  "detail": "One or more fields failed validation.",
  "instance": "/api/v1/dossies",
  "request_id": "req_01JEXEMPLO",
  "retryable": false,
  "errors": [
    {
      "field": "document",
      "code": "invalid_cpf",
      "message": "document must be a valid CPF"
    }
  ]
}
```

### Problemas comuns

|  HTTP | `code`                                                  | Ação recomendada                                                 |
| ----: | ------------------------------------------------------- | ---------------------------------------------------------------- |
| `400` | `validation_error`                                      | corrija os campos e use nova `Idempotency-Key`                   |
| `400` | `invalid_cursor`                                        | inicie uma nova paginação com os mesmos filtros                  |
| `400` | `invalid_path`, `invalid_content_length`                | corrija o path ou o header antes de reenviar                     |
| `401` | `missing_api_key`, `invalid_api_key`, `revoked_api_key` | corrija ou substitua a credencial                                |
| `402` | `insufficient_balance`, `payment_required`              | regularize saldo ou assinatura                                   |
| `403` | `scoped_key_required`, `key_entitlement_missing`        | emita uma chave scoped com o produto habilitado                  |
| `403` | `insufficient_scope`, `entitlement_not_enabled`         | ajuste os scopes ou habilite o produto no workspace              |
| `404` | `resource_not_found`                                    | confira o ID no workspace atual                                  |
| `405` | `method_not_allowed`                                    | use um dos verbos anunciados no header `Allow`                   |
| `409` | `invalid_state_transition`, `result_not_ready`          | consulte o recurso e respeite `allowed_actions` ou `Retry-After` |
| `409` | `idempotency_in_progress`                               | aguarde `Retry-After` e repita com a mesma key                   |
| `409` | `refund_pending`, `prior_refund_pending`                | aguarde a liquidação do refund antes de tentar de novo           |
| `413` | `payload_too_large`                                     | reduza o corpo ou arquivo                                        |
| `415` | `unsupported_media_type`                                | envie um formato aceito                                          |
| `422` | `unsupported_subject`, `unsupported_mode`               | ajuste o tipo de alvo ou modo                                    |
| `429` | `rate_limit_exceeded`, `quota_exceeded`                 | respeite `Retry-After` e os limites vigentes                     |
| `502` | `bad_gateway`                                           | repita operações seguras com a mesma key e back-off              |
| `504` | `gateway_timeout`                                       | repita operações seguras com a mesma key e back-off              |

Respostas temporárias podem trazer `retry_after_seconds` no corpo e
`Retry-After` no header. Nunca faça retry automático de um erro não marcado como
`retryable`.

### Limites de transporte

Corpos JSON das APIs de produto aceitam no máximo **2 MiB**. O Motor de Borderô
mantém limites próprios de **128 MiB** para o CNAB, **512 MiB** para o ZIP de NFe
e **768 MiB** para o multipart completo, incluindo campos e framing. Uploads
chunked são aceitos e contados durante o stream; ao ultrapassar o teto, o gateway
aborta o envio ao upstream e retorna `413 payload_too_large`.

## Polling, eventos e webhooks

Polling é o contrato autoritativo. Eventos duráveis usam cursor e sequência por
recurso. SSE e webhooks são conveniências de baixa latência e não iniciam nem
sustentam uma execução.

Webhooks são opcionais. Um endpoint novo começa `active` depois da validação de
URL; a entrega aplica assinatura, proteção contra SSRF, retry, DLQ e replay. A
entrega é `at-least-once`, portanto deduplique por `event.id`.

| Método  | Path                                                      | Scope            | Resposta | Finalidade                         |
| ------- | --------------------------------------------------------- | ---------------- | -------: | ---------------------------------- |
| `POST`  | `/webhook-endpoints`                                      | `webhooks:write` |    `201` | criar endpoint e revelar o segredo |
| `GET`   | `/webhook-endpoints`                                      | `webhooks:read`  |    `200` | listar endpoints                   |
| `GET`   | `/webhook-endpoints/{id}`                                 | `webhooks:read`  |    `200` | ler configuração e saúde           |
| `PATCH` | `/webhook-endpoints/{id}`                                 | `webhooks:write` |    `200` | alterar URL, eventos ou status     |
| `POST`  | `/webhook-endpoints/{id}/rotate-secret`                   | `webhooks:write` |    `200` | rotacionar e revelar novo segredo  |
| `GET`   | `/webhook-endpoints/{id}/deliveries`                      | `webhooks:read`  |    `200` | listar entregas, retries e DLQ     |
| `POST`  | `/webhook-endpoints/{id}/deliveries/{delivery_id}/replay` | `webhooks:write` |    `202` | reenfileirar uma entrega           |

O `signing_secret` aparece somente na criação e na rotação. Cada `POST` de
entrega inclui `x-sherlocker-event-id`, `x-sherlocker-timestamp`,
`x-sherlocker-secret-version` e `x-sherlocker-signature: v1=<hmac-sha256>`.
Aceite somente HTTPS na porta 443 e devolva `2xx`; `410` desabilita o endpoint.

O webhook carrega apenas IDs, versão, sequência, status, timestamps e um resumo
não sensível. Consulte o recurso com uma chave que tenha `*:read` para obter o
resultado completo.

## Artefatos, retenção e exclusão

Artefatos ficam em armazenamento privado. Quando disponíveis, a resposta inclui
uma URL assinada de curta duração; outra leitura autorizada pode emitir uma nova
URL sem alterar `artifact.status`.

Recursos, resultados, eventos e artefatos usam retenção indefinida e
`available_until: null` na v1. A expiração da URL assinada aparece separadamente
em `expires_at` ou `url_expires_at`, conforme o recurso. Não há endpoint público
de purge. Para uma solicitação de privacidade ou exclusão definitiva, use o
canal de [Suporte](/support).
